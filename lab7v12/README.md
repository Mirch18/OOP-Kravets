# Лабораторна робота №7

**Тема:** Узагальнені типи (Generics). `IRepository` з `where`-обмеженнями та тестами.

**Мета:** Навчитися створювати узагальнені інтерфейси та класи, застосовувати `where`-обмеження для типів-параметрів, а також розробляти юніт-тести для перевірки коректності узагальнених реалізацій (варіант 12: сутність `Car`).

## Хід роботи

У ході виконання роботи за допомогою .NET CLI у директорії `OOP-Kravets` було створено консольний проєкт `lab7v12` та проєкт тестів `lab7v12.Tests` (xUnit), до якого додано посилання на основний проєкт:

```bash
dotnet new console -o OOP-Kravets/lab7v12
dotnet new xunit -o OOP-Kravets/lab7v12.Tests
cd OOP-Kravets/lab7v12.Tests
dotnet add reference ../lab7v12/lab7v12.csproj
```

У проєкті `lab7v12` реалізовано:

- **Інтерфейс `IEntity`** (`IEntity.cs`): містить властивість `int Id { get; set; }`, яку має кожна сутність.
- **Узагальнений інтерфейс `IRepository<T>`** (`IRepository.cs`): методи `GetById(int id)`, `GetAll()`, `Add(T item)`, `Update(T item)`, `Delete(int id)`. На тип-параметр накладено обмеження `where T : IEntity`, тому репозиторій працює лише з сутностями, що мають `Id`.
- **Клас `InMemoryRepository<T>`** (`InMemoryRepository.cs`): реалізує `IRepository<T>` і зберігає дані у пам'яті в `List<T>`. Пошук елемента виконує приватний метод `FindIndex(int id)`.
  - `Add` — додає елемент; якщо елемент з таким `Id` вже існує, викидає `InvalidOperationException`, для `null` — `ArgumentNullException`.
  - `GetById` — повертає елемент за `Id`; для неіснуючого `Id` викидає `KeyNotFoundException`.
  - `GetAll` — повертає копію списку всіх елементів.
  - `Update` — замінює існуючий елемент з тим самим `Id`; для неіснуючого викидає `KeyNotFoundException`.
  - `Delete` — видаляє елемент за `Id`; для неіснуючого викидає `KeyNotFoundException`.
- **Клас сутності `Car`** (`Car.cs`): реалізує `IEntity`, має властивості `Brand` (string), `Model` (string), `Year` (int), конструктор і перевизначений `ToString()`.

У проєкті `lab7v12.Tests` (`InMemoryRepositoryTests.cs`) написано 11 юніт-тестів з використанням методів `Assert`:

| Метод | Тести |
|---|---|
| `Add` | додавання нового елемента; додавання елемента з існуючим `Id`; додавання `null` |
| `GetById` | отримання існуючого елемента; запит неіснуючого `Id` |
| `GetAll` | отримання всіх елементів; порожній репозиторій |
| `Update` | оновлення існуючого елемента; спроба оновити неіснуючий |
| `Delete` | видалення існуючого елемента; спроба видалити неіснуючий |

У точці входу `Main`:

1. Створено екземпляр `InMemoryRepository<Car>` через посилання типу `IRepository<Car>`.
2. Додано три автомобілі та виведено їх список.
3. Отримано автомобіль за `Id`, оновлено один автомобіль і видалено інший.
4. Продемонстровано обробку помилкових ситуацій: запит, оновлення та видалення неіснуючого елемента, додавання дубліката `Id`.

## Відповіді на контрольні запитання

1. **Яка роль `where`-обмежень у Generics? Наведіть приклади їх використання.**

   `where`-обмеження визначають, які типи можна підставити замість типу-параметра, і водночас дають змогу компілятору знати, які члени цього типу доступні. У роботі обмеження `where T : IEntity` гарантує, що кожен `T` має властивість `Id`, тому в `InMemoryRepository<T>` можна написати `item.Id`. Інші приклади: `where T : class` — лише посилальні типи, `where T : struct` — лише типи-значення, `where T : new()` — тип повинен мати конструктор без параметрів, `where T : IComparable<T>` — тип має вміти порівнюватися.

2. **Навіщо потрібен шаблон `IRepository`? Які переваги він дає?**

   Шаблон `IRepository` відокремлює логіку доступу до даних від решти програми. Код, що використовує репозиторій, працює з інтерфейсом і не знає, де саме зберігаються дані — у списку в пам'яті, у файлі чи в базі даних. Це дає змогу замінити реалізацію (наприклад, `InMemoryRepository<T>` на репозиторій для бази даних) без змін в іншому коді, а також спрощує тестування. Узагальнений `IRepository<T>` до того ж позбавляє від дублювання: одна реалізація підходить для `Car`, `Product` чи будь-якої іншої сутності.

3. **Поясніть, чому юніт-тести є важливими при розробці узагальнених компонентів.**

   Узагальнений компонент використовується з багатьма типами, тому помилка в ньому проявиться всюди, де його застосовано. Юніт-тести автоматично перевіряють, що кожен метод працює правильно, зокрема у граничних випадках: неіснуючий `Id`, дублікат, порожній репозиторій. Після будь-якої зміни коду достатньо запустити `dotnet test`, щоб переконатися, що нічого не зламалося.

4. **Які проблеми вирішують Generics порівняно з використанням `object`?**

   Якщо зберігати дані як `object`, компілятор не перевіряє типи: у колекцію можна випадково покласти об'єкт іншого класу, а при отриманні потрібне явне приведення типу, яке може завершитися помилкою під час виконання. Для типів-значень (`int`, `double`) ще й відбувається упаковка (boxing) і розпаковка, що знижує продуктивність. Generics забезпечують перевірку типів під час компіляції, не потребують приведення і не виконують зайвої упаковки.
